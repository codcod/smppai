[#server]
= The server

`SMPPServer` is a minimal SMSC: it accepts client connections, handles
binds, authentication, `submit_sm` and `enquire_link`, and lets you push
`deliver_sm` to bound clients. It ships with a multi-stage graceful
shutdown sequence.

[#server-high-level-api]
== High-level API

For most servers, `smpp.Server` is all you need. It takes the shutdown
settings in its constructor and registers handlers with decorators; each
handler may be a plain function or `async def`:

[source,python]
----
import smpp

server = smpp.Server(port=2775, shutdown=smpp.Shutdown(grace=10, reminder=5))

@server.authenticate
async def authenticate(system_id, password, system_type):
    return await accounts.check(system_id, password)

@server.on_submit
async def on_submit(session, msg):
    print(session.system_id, msg.sender.addr, "->", msg.to.addr, msg.text)
    return await store.save(msg)  # a message ID string, or None

await server.serve_forever()
----

`Server(host="localhost", port=2775, *, shutdown=None, **server_kwargs)`::
Wraps an `SMPPServer`; extra keyword arguments (`system_id`,
`interface_version`, `max_connections`, `setup_signal_handlers`) go to its
constructor. `start()`, `stop()`, `serve_forever()` and `async with` work as
described below for `SMPPServer`.

`Shutdown(grace=30.0, reminder=10.0, timeout=30.0)`::
The graceful shutdown settings, applied through `configure_shutdown()`, so
an invalid value raises the same `ValueError` or `TypeError` at
construction. Leaving `shutdown` out keeps these same defaults.

`@server.authenticate`::
`fn(system_id, password, system_type) -> bool`. Returning `False` refuses
the bind with `ESME_RBINDFAIL`. Registering again replaces the handler.

`@server.on_submit`::
`fn(session, msg: Message) -> str | None`, called once per `submit_sm`.
`msg` is the same `smpp.Message` the client yields: `sender`, `to`, `text`
(decoded, without any UDH, or `None` when it can't be decoded), and `pdu`
(the `SubmitSm`); `receipt` is always `None`. A concatenated message
arrives as one call per part, since each part's `submit_sm_resp` must carry
its own message ID before the next part is sent. Returning a string sets
that part's message ID; `None` keeps the generated one. Raising answers
`ESME_RSUBMITFAIL`, so the client can retry. Registering again replaces the
handler.

`server.raw`::
The underlying `SMPPServer`, for every other callback (`on_client_bound`,
`on_query_sm`, `on_data_sm`, ...) and for `deliver_sm`. Its `authenticate`
and `on_message_received` belong to the decorators. `on_submit` does not
cover `data_sm`: set `server.raw.on_data_sm` to accept it, otherwise every
`data_sm` is refused with `ESME_RINVCMDID`.

The rest of this chapter documents that low-level `SMPPServer`.

== Constructing and running

[source,python]
----
from smpp import SMPPServer

server = SMPPServer(
    host="0.0.0.0",
    port=2775,
    system_id="SMSC",             # <= 15 chars
    interface_version=0x34,
    max_connections=100,
    setup_signal_handlers=True,   # install SIGTERM/SIGINT handlers
)

await server.serve_forever()  # starts, blocks until shutdown, then stops
----

`serve_forever()` drives the whole lifecycle itself, so don't also wrap the
server in `async with server:` around it — `__aenter__` would call
`start()` a second time and raise `SMPPException`. Use `async with`
instead when you want to drive things yourself: it calls `start()` on
entry and the graceful `stop()` sequence on exit, so you `await` your own
work (other coroutines, a signal you define, polling `shutdown_requested`)
in between rather than `serve_forever()`. Or skip both and call
`await server.start()` / `await server.stop()` directly. `client_count` and
`is_running` report live state regardless of which pattern you use.

`interface_version` (an int, `0x00`-`0xFF`, checked at construction) is
reported to v3.4 ESMEs as the `sc_interface_version` TLV on a successful
`bind_*_resp`. v3.3 ESMEs never get it, since they can't parse TLVs, and
neither does anyone when the server itself is set below `0x34`. Each `ClientSession` records the version its peer bound
with in `session.interface_version` — `0x33` means send it no TLVs.

== Authentication

[source,python]
----
def authenticate(system_id: str, password: str, system_type: str) -> bool:
    return valid_clients.get(system_id) == password

server.authenticate = authenticate
----

The default `authenticate` accepts every bind. Only one callback is
supported at a time (assigning replaces it); it may be sync or async.

== Handling messages from clients

[source,python]
----
def handle_message(server, session, pdu: SubmitSm) -> str | None:
    print(f"{session.system_id}: {pdu.source_addr} -> {pdu.destination_addr}")
    return None  # or a custom message ID string

server.on_message_received = handle_message
----

Returning a string from `on_message_received` overrides the server's
auto-incrementing message ID in the `submit_sm_resp`; returning `None`
keeps the default. A non-string ID, such as a database row id, is converted
with `str()`. If the handler raises, the exception is logged with
`logger.exception` and the server answers `ESME_RSUBMITFAIL` with no message
ID. It doesn't acknowledge a message that may have been lost, so the client
can retry. `submit_sm` is rejected with `ESME_RINVBNDSTS` unless the
sending session is bound as transmitter or transceiver.

`data_sm` goes to `on_data_sm` instead, which works the same way: return a
message ID string or `None`, and the server replies with `data_sm_resp`.
Read the content with `pdu.get_message_text()` or
`pdu.get_message_payload()`. `on_message_received` never sees a `data_sm`.
Without an `on_data_sm` handler the server refuses every `data_sm` with
`data_sm_resp` `ESME_RINVCMDID` and no message ID, since nothing would
receive it.

== Event handlers

Every callback may be a plain function or `async def`; an async one is
awaited at the point the sync one would be called, so the server still
replies with its result.

[cols="1,3"]
|===
| Handler | Signature

| `on_client_connected`
| `(server, session: ClientSession) -> None` — TCP accepted, before any bind.
  To reject the client, `await session.connection.disconnect()`. The server
  then closes the socket without reading any PDU; `on_client_disconnected`
  is not called for a rejected client.

| `on_client_disconnected`
| `(server, session: ClientSession) -> None` — socket closed, bound or not.

| `on_client_bound`
| `(server, session: ClientSession) -> None` — bind accepted.

| `on_message_received`
| `(server, session: ClientSession, pdu: SubmitSm) -> Optional[str]` — see above.

| `on_data_sm`
| `(server, session: ClientSession, pdu: DataSm) -> Optional[str]` — like
  `on_message_received`, for `data_sm`; see above.

| `on_query_sm`
| `(server, session: ClientSession, pdu: QuerySm) -> Optional[tuple[int, str, int]]` —
  return `(message_state, final_date, error_code)`. Returning `None` (or
  leaving the handler unset, or raising — logged with `logger.exception`)
  answers `ESME_RQUERYFAIL`.

| `on_cancel_sm`
| `(server, session: ClientSession, pdu: CancelSm) -> bool` — return `True`
  to acknowledge the cancel. Returning `False` (or leaving the handler
  unset, or raising) answers `ESME_RCANCELFAIL`.

| `on_replace_sm`
| `(server, session: ClientSession, pdu: ReplaceSm) -> bool` — return `True`
  to acknowledge the replace. Returning `False` (or leaving the handler
  unset, or raising) answers `ESME_RREPLACEFAIL`.
|===

`query_sm`, `cancel_sm` and `replace_sm` are rejected with
`ESME_RINVBNDSTS` unless the sending session is bound as transmitter or
transceiver, the same check `submit_sm` uses. The server never answers any
of the three with `generic_nack`, and it keeps no message store of its
own — the application's callback owns whatever state it needs.

`ClientSession` (from `smpp.server`) exposes `system_id`, `bind_type`
(`'transmitter'`/`'receiver'`/`'transceiver'`/`''`), `bound`, `address_range`,
`message_counter` and the underlying `connection`.

`get_client_sessions()` and `get_bound_clients()` return the current
sessions (all, and bound-only, respectively).

== Delivering to a client

[source,python]
----
delivered = await server.deliver_sm(
    target_system_id="my_client",
    source_addr="SYSTEM",
    destination_addr="my_client",
    short_message="Hi there",
    data_coding=DataCoding.DEFAULT,
)  # bool
----

`deliver_sm` looks up a bound session by `system_id` (must be bound as
receiver or transceiver) and returns `False` — never raises — if no
matching session exists or the send fails.

[#server-shutdown]
== Graceful shutdown

`stop()` (and the signal handlers installed when `setup_signal_handlers=True`)
runs a staged sequence rather than dropping connections immediately:

. Stop accepting new connections and new messages.
. Wait up to `shutdown_timeout` seconds for in-flight handlers (a slow
  `on_message_received`, say) to finish and send their responses. Any handler
  still running after that is cancelled.
. Broadcast a shutdown notification (a `deliver_sm`) to every bound
  receiver/transceiver client.
. Wait up to `grace_period` seconds for clients to unbind and disconnect on
  their own.
. If any remain bound, broadcast a reminder and wait
  `reminder_delay` more seconds.
. Send `unbind` to any clients still bound (10s budget).
. Force-disconnect whatever's left, capped at `shutdown_timeout`.

Configure the timings with one call:

[source,python]
----
server.configure_shutdown(grace_period=15.0, reminder_delay=5.0, shutdown_timeout=10.0)
----

or individually with `set_shutdown_grace_period()`,
`set_shutdown_reminder_delay()` and `set_shutdown_timeout()`. All setters
validate their argument (non-negative, capped at one or two hours) and raise
`ValueError`/`TypeError` on bad input. `get_shutdown_config()` returns the
current values plus `shutdown_in_progress`, `accept_new_connections` and
`accept_new_messages`. `shutdown_requested` (property) reports whether
shutdown has been triggered, by signal or by `stop()`.

A client that wants to participate gracefully watches `on_deliver_sm` for
these notifications and disconnects on its own once it sees one — see
`examples/client_advanced.py` for a complete implementation of that side.

=== Client unbind

When a client sends `unbind`, the server marks the session unbound and then
lets that session's earlier requests finish first. It waits up to 10 seconds
for their handlers to send responses, and cancels any handler still running
after that. It then sends `unbind_resp`, closes the connection and calls
`on_client_disconnected`. Requests that arrive after the `unbind` are refused
(`submit_sm` with `ESME_RINVBNDSTS`). A bind that races the unbind, including
one still waiting on an async `authenticate`, gets `ESME_RBINDFAIL`.

`on_client_disconnected` fires once per session, whether the client unbinds,
drops the connection, or is disconnected by `stop()`.
